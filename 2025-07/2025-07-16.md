## 学習内容1  
- **タグ**: LINE
- **タイトル**: LINEのプッシュ通知(Messaging API)
- **内容**: 
  - LINEのプッシュ通知（Messaging API）は、Botサーバー側から任意のタイミングでユーザーへメッセージを能動的に送信できる機能。
    - プッシュ通知は、ユーザーの操作（Webhook経由のReply）を待たずにBot側から直接メッセージを送信する。
      - Webhookとは、LINEプラットフォーム側からユーザーの操作（メッセージ送信、友だち追加など）を検知して、開発者のあらかじめ設定したサーバー（Webhook URL）へHTTPリクエスト（POST）で通知を送る仕組み。サーバーは受け取ったイベントの中のreplyTokenを使い、Reply API（POST /v2/bot/message/reply）を呼び出して応答メッセージを返す。Replyはイベントを受け取った返信を行うためのもので、送信先ユーザーを自動で解決。
    - エンドポイントは`POST /v2/bot/message/push`を利用。
    - 送信可能なメッセージタイプはテキスト、ステッカー、イメージ、動画、テンプレート、Flex Messageなど。 
  - 導入前の準備
    - LINE公式アカウントの作成
      - LINE Official Account Managerで公式アカウントを作成し、Business ID登録。
      - Messaging APIを有効化し、チャネル（Channel）を発行。
      - チャネル情報の取得、「チャネルシークレット（Channel secret）」と「チャネルアクセストークン（Channel access token）」をLINE Developersコンソールから取得。
        - チャネルシークレット: BotのWebhook署名検証に使う秘密鍵のようなもの。サーバーはWebhookリクエストに含まれるX-Line-Signature（署名）ヘッダーを、このシークレットでHMAC-SHA256検証して「本物のLINEプラットフォームから来た」ことを確認。
        - チャネルアクセストークン: LINE Platformへのリクエストを行う際に、サービス提供者のチャネルを利用する権限があることを示すトークン。BotサーバーがReply/Pull/Push APIを呼び出す際の認証トークン。通常は「長期（ロング）/短期（ショート）」の2種類があり、LINE Developersコンソールで発行。リクエスト時はHTTPヘッダーにセットして送信元の正当性を示す。
      - Push Messageを送る際には、HTTPヘッダー`Authorization: Bearer {Channel access token}`を必須で付与。
        - ヘッダー名：Authorization
        - 認証方式  ：Bearerスキーム
        - トークン  ：発行されたチャネルアクセストークン
        - 役割      ：LINEプラットフォーム側で「このリクエストは有効なBotからのもの」と認証・許可 
  - 実装の流れ
    - HTTPクライアント（Faraday、HTTParty、あるいは公式SDK）を用意
      - ここでいうHTTPクライアントとは、Webサーバー（Railsアプリ）から別のサーバー（LINE Platform）のAPIを呼び出すための窓口となるライブラリ。
      - 生のNet::HTTPを使うこともできるが、以下のような高機能ライブラリを使うと、エラーハンドリング、タイムアウト設定、リクエスト/レスポンスのロギングなどが簡単になる。
      - 代表的なライブラリは以下の通り
        - Faraday     : プラグイン方式で拡張性が高く、ミドルウェアが豊富
        - HTTParty    :	設定が少なく、「classに設定を書くだけ」で使える手軽さ
        - official SDK:	LINEが提供しているRuby向けのSDK(line-bot-sdk-ruby)
  - 運用上の注意点
    - 特定の日程や時期の通知を行う場合、サーバー側のスケジューラー（cronやHeroku Schedulerなど）からPush APIを叩くのが一般的。
    - 無料プラン（コミュニケーションプラン）にはメッセージ送信数月間200通という制限あり。だし自動返信（Reply API）等以下の方法で送るメッセージは含まれない。
      - LINEチャットの送受信
      - 応答メッセージ
      - あいさつメッセージ
      - Messaging APIの「Reply API」

## 学習内容2  
- **タグ**: RBS, Ruby
- **タイトル**: RBS（Ruby Signature）
- **内容**: 
RBS（Ruby Signature）は、Ruby3.0から導入された「型定義ファイルのフォーマット言語」。  
Rubyのクラス・モジュールの構造（メソッド名・引数の型・戻り値の型・定数・継承関係など）を.rbs拡張子のファイルに宣言しておくことで、以下のようなメリットが得られる。
  - 静的型チェックができる
    - SteepやTypeProfといったツールが、RBSファイルを読み込んでコードの型整合性を検査。
    - 「このメソッドはStringを返すはずなのにIntegerを返している」というようなバグを事前に発見。 
  - エディタ補完・ナビゲーションが賢くなる
    - VSCodeなどのエディタが、RBSを参照してメソッドのシグネチャやドキュメントを表示。
    - .rbsがあることで「引数は何型か、返り値は何か」がすぐわかり、開発効率が上がる。 
  - ドキュメント代わりにも使える
    - Gemや標準ライブラリが提供するRBSを読むだけで、APIの使い方が把握可能。
    - `rbs collection install`コマンドで、依存Gemの型定義をまとめて取得できる仕組みもある。 
```
# 例
  # initializeメソッドは、StringとIntegerを受け取ってvoidを返す
  def initialize: (name: String, age: Integer) -> void

  # greetメソッドは、引数なしでStringを返す
  def greet: () -> String
end
```
この.rbsを用意すると、
  - `MyClass.new(123, "foo")`と書くと「第1引数はStringのはず」と警告が出る。
  - `my_obj.greet.length`と書くと「greetはStringを返すのでlength呼べます」と補完が効く。

## 学習内容3  
- **タグ**: Rails
- **タイトル**: ActiveJobとは
- **内容**: 
  - 概要
    - ActiveJobとは、ジョブを宣言しそれによってバックエンドでさまざまな方法によるキュー操作を実行するためのフレームワーク。  
    - ジョブには、定期的なクリーンアップを始めとして、請求書発行やメール配信など、あらゆる処理がジョブになる。  
    - これらのジョブをより細かな作業単位に分割して並列実行することも可能。  
      - Job   : コンピュータがする仕事の単位（一つ一つのタスク）。
      - Queue : データ構造の一つ。待ち行列とも（複数のタスクをまとめたもの）。
    - ActiveJobはバックグラウンドで実行ができるため、処理をアプリケーションの裏側で実行させることが可能。  
    - そのためActiveJobは基本的にリアルタイム性を伴わない場合や重たい処理に使われることが多い。  
    - 具体的には以下のようなもの。  
      - メールの送信
      - 画像の処理
      - データを集計してCSVに落とす  
  - ActiveJobと非同期バックエンド
    - ActiveJobには非同期バックエンドなるサードパーティーのキューイングライブラリが必要。
    - 開発環境や、小規模アプリケーションの場合にはActiveJobのみでも問題ないが、本番環境でアプリケーションを運用していくとなるといろいろと不都合がでてくる。
      - Railsから提供されているActiveJobには、ジョブをメモリに保持するインプロセスのキューイングシステムだけなので、プロセスが切れたりするとジョブは全て失われます。
    - よく採用される非同期バックエンド
      - Sidekiq
        - Sidekiqは別プロセスを立てるため、Railsプロセスが終了したとしても問題がなくリトライも可能。しかしジョブを永続化するために、RedisといったNoSQLも必要に。
      - sucker_punch等。
        - sucker_punchは非同期処理をスレッドで実行するため、Railsとプロセスを分ける必要がない。
        - 万が一ジョブの実行中にRailsの再起動をすると、実行中のジョブは強制的に中断され、再起動後のリトライも自動では実行されない。
      - DeployedJob
      - Resque
    - ActiveJobを使用せず、Sidekiqを利用する
      - ActiveJobを使用せず直接Sidekiqを使用するということも可能。しかし多くのプロジェクトではActiveJob経由してSidekiqを利用する。そうすることで、非同期処理のライブラリがSidekiqから他のライブラリに変わったとしてもコードの流用が可能。
    - ActiveJobの同期実行
      - 同期実行も可能。ケースとしてはジョブの実行結果をテストする時等。
      ```
      # config/environments/test.rb
      Rails.application.config.active_job.queue_adapter = :inline
      ```
