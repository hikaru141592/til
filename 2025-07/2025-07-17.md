## 学習内容1  
- **タグ**: Dockerfile, Docker
- **タイトル**: Dockerfileのコード解説(entrypoint.shについて)
- **内容**: 
```
COPY entrypoint.sh /usr/local/bin/entrypoint.sh
```
  - COPY
    - Dockerfileの命令（Instruction）のひとつで、ホスト（ビルドコンテキスト）上のファイルやディレクトリをイメージ内にコピー。
      - ビルドコンテキスト
        - docker buildコマンドを実行したときにDockerが中身を全部見るために取り込むディレクトリのこと。
        - 通常は、Dockerfileと同じ階層（あるいは`docker build ./path`のpath）のディレクトリ以下すべてが対象。
        - ここに含まれるファイルだけが、COPYやADDでイメージに取り込む元として指定可能。
  - entrypoint.sh
    - ビルドコンテキスト内に用意しておくスクリプトファイル。必ず事前に用意しておく必要がある。
    - Dockerコンテナが起動するときに必ず最初に実行されたいシェルスクリプトを記述しておく。
    - entrypoint.shの一般的な使い方
      - マイグレーションやプリコンパイルなどの前準備を自動化
      - 環境変数の読み込み
  - /usr/local/bin/entrypoint.sh
    - /usr/local/binはUNIX 系でユーザー管理の実行可能プログラムを置く場所として慣例的に使われる。

  - 備考
    - その後は`RUN chmod +x 略`で実行権限を付与し、ENTRYPOINT [`/usr/local/bin/entrypoint.sh`]で実行。

## 学習内容2  
- **タグ**: Dockerfile, Docker
- **タイトル**: DockerにおけるレイヤーとInstruction
- **内容**: 
Dockerイメージはレイヤー（層）の積み重ねで構成されていて、Dockerfileの各命令は基本的に１つずつレイヤーを追加する。
ビルド時に変更のないレイヤーは再実行をスキップすることで高速化を図っている。
  - レイヤーが増えるDockerfileの命令（Instruction）
    - FROM    ：ビルドのベースとなるイメージの最初のレイヤーを指定
      - 例：`FROM ruby:3.2.2`
    - RUN     ：コンテナ内でシェル（デフォルトだと /bin/sh -c）を起動し、ビルド時に指定のコマンドを実行し新しいレイヤーを追加。
    - COPY    ：ビルドコンテキスト（ホスト側の指定ディレクトリ）からイメージ内にファイルやディレクトリをコピーし新しいレイヤーを追加。
    - ADD     ：COPYの機能に加え、URLからダウンロードして展開、ローカルのtarアーカイブを自動展開が可能、そして新しいレイヤーを追加。
    - WORKDIR ：`WORKDIR /myapp`のようにすると以降のRUNやCOPYがデフォルトで/myappを基準に実行されるように、メタデータとしてレイヤーを追加する。
      - ファイルの追加や削除を行うわけではなく、イメージのメタ情報を更新。
    - ENV     ：環境変数を設定。以降のビルド中またはコンテナ起動時に有効。
      - ファイルの追加や削除を行うわけではなく、イメージのメタ情報を更新。
    - CMD     ：コンテナ起動時に実行したいコマンドを指定。
      - 実行時の設定を行うものでファイルシステムには変更を加えず、レイヤーを追加しないことが多いが、Dockerの実装によってはメタデータ更新レイヤーとしてカウントされる場合も。
    - ENTRYPOINT：コンテナ起動時に実行したいバイナリやスクリプト本体を指定。
      - 実行時の設定を行うものでファイルシステムには変更を加えず、レイヤーを追加しないことが多いが、Dockerの実装によってはメタデータ更新レイヤーとしてカウントされる場合も。

## 学習内容3  
- **タグ**: cron, whenever
- **タイトル**: cron+wheneverのつまずいたポイントメモ。
- **内容**:
  1. Bundlerバージョンずれ
    - `bundler 2.4.10`でbundle installしてGemfile.lockで2.4.10となっていたが、OSが自動で入れるbundleが2.6.8でcron実行時にBundler::GemNotFound
    - Dockerfileで統一バージョンを固定(ARG BUNDLER_VERSION=2.6.8で一括更新できる)。
  2. cronがGemを見失う
    - Gemは/usr/local/bundleに入れたのにGEM_PATH=/usr/local/lib/ruby/gems/3.2.0を渡していた。
    - cron実行時だけ再びGemNotFound。
    - schedule.rbの環境変数(BUNDLE_PATH,GEM_HOME,GEM_PATH)を/usr/local/bundleに統一。
  3. cronジョブが消える
    - コンテナ再起動したらcrontab -l がno crontab。
    - コンテナはstateless。`whenever --update-crontab`を毎回実行しないと登録が消える。
    - entrypoint.shで起動のたびに登録＋cron起動とした。
  4. ジョブが実行されているはずなのにcron.logが増えない
    - runnerはRails.loggerを使うのでdevelopment.logに出る。
  5. デバッグ、チェックコマンド
    - cronが動いてるか：`ps -ef | grep cron`
    - crontab登録確認：`crontab -l`
    - 今のBundlerバージョン：`bundle -v`
    - rails runner単発テスト：`rails runner XXX`
    - cron.logをリセット：truncate -s 0 log/cron.log
  6. 学び
    - Bundlerのバージョンはbuildとrunで必ず揃える。
    - /usr/local/bundleをGemの標準パスに固定する。
    - statelessコンテナではcrontabを起動時に毎回生成。
    - ログ出力はRails.loggerなのかSTDOUTなのかを意識してファイルを見に行く。
