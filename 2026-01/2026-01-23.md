# バックエンドフレームワークの変遷

## 1. 1990 年代後半：黎明期（フレームワーク以前）

### 主流

- Perl + CGI
- PHP（初期）
- Classic ASP

### 状況

- 動的 HTML を返せれば十分
  - お問い合わせフォーム、簡単な掲示板、会員登録程度
- 設計思想・構造化はほぼ無し
- スクリプト直書き文化
  - HTML 生成や DB 処理認証ロジックなど全部を同じファイルで処理
  - 共通処理はコピペ

### 衰退理由

- スパゲッティコード化
- 保守不能・再利用不能

### 備考

- PHP は形を変えて現在でも生存

---

## 2. 2000 年代前半：MVC フレームワークの台頭

- 「ページを返す」から「状態と振る舞いを持つアプリを作る」へ
  - 後の Rails・Django・Spring すべての土台となる。

### インターネットの変化

- 個人サイト中心 → 企業サイト・会員制サービス
- 必要になったもの
  - ログイン、セッション
  - 権限管理
  - DB 中心設計
- チーム開発が主流に
- MVC の概念が生まれる、思想ではなく実用となる
- Web 開発が職人芸から工業製品になった瞬間

### 主流

- Struts（Java）
  - Web アプリの先駆者
  - 開発が遅いなどを理由に廃れる
- CakePHP
  - PHP 自体が未成熟
- Django（Python）
  - ニュースサイト、メディア企業、情報量が多いサイトを現実に運用するために生まれる。
  - セキュリティ重視、堅実、保守的
  - 企業・官公庁・長期運用に向く
- Ruby on Rails
  - 人間が気持ちよく書けることを最優先する
    - 設定より規約
    - ORM（ActiveRecord）
    - REST
      - URL は“操作”ではなく“対象（資源）”を表すという考え
  - 開発速度が桁違い
    - スタートアップ向け
  - Web 開発の作法を定義した
    - 他言語が追随

## 3. 2000 年代後半〜2012 年：フルスタックが主流に

- Web アプリ開発の完成形が一度“確定”した時代
- MVC + ORM + 認証 + 画面 + DB ＝ フルスタックフレームワーク が正解とされた時代

### 当たり前になった要件

- ログイン / ログアウト
- 権限管理
- CRUD 画面
- 管理画面
- メール送信
- バリデーション
- DB 中心設計

### フルスタックとは何を指したか（当時）

- Web アプリに必要なものが最初から全部ある
  - MVC
  - ORM
  - ルーティング
  - テンプレートエンジン
  - 認証・セッション
  - バリデーション
  - 開発用ツール一式

## 主流

### Ruby on Rails

- この時代の基準点
- 「まず Rails で作る」が常識
- Rails にとっての全盛期

### Django

- Rails に次ぐ完成度

### Laravel（PHP）

- Rails の思想を強く取り込んだ
- 開発体験の改善

## フルスタック

- フロント分離がまだ一般的でない
- SPA(Single-page application) 未成熟
  - MPA: サーバー → HTML 生成　ブラウザ → 表示のみ
    - リンクやボタンをクリックするごとに新しいページがサーバーから取得される仕組み
    - ユーザーがページ間を遷移するたびにサーバー側で生成された新しい HTML がダウンロードされ画面全体がリフレッシュされる
  - SPA: サーバー → JSON を返す　ブラウザ → 画面を組み立てる
    - ページの読み込み時に必要なデータやリソースを一度に取得
    - サーバーとのやり取りを最小限に抑えて動的なコンテンツの表示や操作を行う
- サーバーサイドで HTML 生成が主流

### 備考

- テストを書く文化が芽生える
- Git が広まり始める
- チーム開発がより標準に
- この時代を WEB 開発の黄金期と呼不ことも
  - 技術が安定していた
  - 選択肢が多すぎなかった
  - 生産性が非常に高かった
  - 成功体験が量産された

## 4. 2013〜2017 年：SPA × API 分離

### フロントエンドとバックエンドが初めて本格的に役割分担

- 画面が重くなる
- JS が強くなる
  - Ajax：JavaScript と XML を使って非同期にサーバとの間の通信する
- フロント分離
- SPA 登場
  - 表示責任がサーバーからクライアントへ移動
  - API 分離

### フロントエンドフレームワーク

- Angular（2010）
  - Google が開発した、大規模 Web アプリケーションのフロントエンド開発に適した、TypeScript ベースの強力なフレームワーク
- React（2013）
  - Meta 社が開発した UI を効率的に構築するための JavaScript ライブラリ、コンポーネントベースの設計と仮想 DOM という特徴を持ち、コンポーネントを組み合わせて UI を作ることで開発の効率化と高いパフォーマンスを実現
- Vue（2014）
  - 同様に UI を作るための JavaScript フレームワークで、初心者でも学びやすくコンポーネント指向で効率的な開発が可能、また段階的な導入・拡張がしやすい点が特徴。

### API 分離による役割分担の明確化

- バックエンド：
  - 認証
  - ビジネスロジック
  - DB 操作
  - JSON API 提供
- フロントエンド：
  - 画面
  - UI/UX
  - 状態管理

### 画面を作らないバックエンド誕生

- フルスタックは重いと見なされ始める
- 求められたバックエンドの条件
  - 軽量
  - 速い
  - API が書きやすい
  - HTML 不要

## 新しく台頭したフレームワーク

### Node.js（Express）

- ブラウザ上という制限された環境でしか動けなかった JavaScript を、Python や Ruby のようにサーバー上で動かせるようにしてくれた

### Python：Flask

- 最小構成で API 特化
- Django より軽い
- 必要な分だけ足す

### Ruby：Sinatra

- Rails より極端にシンプル
- API 用途・小規模向け
- Rails の影に隠れつつも一定需要

## 既存フレームワークへの影響

### Rails

#### 打撃

- HTML 生成前提が重く見える
- SPA との相性が悪いと言われる

#### 生存戦略

- 以下のように適応して生き残った
  - API モード導入
  - JSON 専用利用
  - フロント分離を許容

### Django

- API 用途に対応
- 堅実だが分離対応はやや後追い

## この時代の失敗と混乱

### 問題点

- 分離したが整っていない状態だった
  - Node.js の無秩序化
    - 急速な採用とエコシステムの爆発的な拡大に開発者の設計スキルや規約（規律）が追いつかず、技術的負債が限界まで溜まった
  - 型なし JS
  - 責務が曖昧

# 5. 2018〜2022 年：型・高速・チーム開発 重視

## 概要

- 「とりあえず動く」より「安全に・速く・チームで作れる」ことが重視された。
- サービスが大きくなってきた
  - 人数が増える
  - 長期間運用する

## この時代に評価されたポイント

- 型がある（ミスに気づきやすい）
- API 仕様が自動で見える
  - プログラムのソースコード（実装）を変更した際に、それに合わせて API の仕様書（API ドキュメント）が自動的に生成・更新され、ブラウザなどで常に最新の仕様を閲覧できる
- チームで書いても破綻しない
- 処理が速い

## よく使われたフレームワーク

### Spring Boot（Java）

- 企業システムの定番
- 安定性・保守性が非常に高い
- 大規模、長期運用、業務システムが得意

### FastAPI（Python）

- シンプルで速い
- API ドキュメントが自動生成される
- API サーバ、AI / データ系、小〜中規模が得意

### NestJS

- Node.js 製（TypeScript 前提）
- 書き方のルールが明確
- Node.js でも安心してチーム開発できる
- フロント連携 API、中規模以上

### Go（Gin / Echo）

- 非常に速い、構造が単純、高負荷に強い
- インフラ寄り API

## 衰退した考え方

- 無秩序な Node.js
  - 自由すぎて壊れやすい
  - 人が増えると破綻
- Rails 一択という考え
- Rails が悪いわけではないが、どんな用途でも Rails とは言えなくなってきた
  - フレームワークは用途で選ぶように

# 6. 2023〜2025 年：「流行っているから使う」から「目的に一番合うものを選ぶ」時代

## 用途、目的

- API？
- 高負荷？
- 社内ツール？
- AI 連携？

## よく使われているフレームワーク

### Rails

- 特徴
  - 速く作れる
  - 仕様変更に強い
  - ビジネスロジックが書きやすい
- 向いてる分野
  - BtoB
  - 管理画面
  - MVP / スタートアップ

### FastAPI（Python）

- 特徴
  - 軽量
  - 速い
  - AI・データ系と相性が良い
- 向いてる分野
  - AI 連携 API
  - データ処理
  - シンプルな API

### NestJS

- 特徴
  - TypeScript 前提
  - フロントとの相性が良い
  - 構造がわかりやすい
- 向いてる分野
  - BFF
  - SPA / モバイル用 API

### Spring Boot

- 特徴
  - 安定性が最優先
  - 企業システムの定番
- 向いてる分野
  - 大規模
  - 業務・基幹系
  - 長期運用

### Go

- 特徴
  - 非常に速い
  - 構成がシンプル
- 向いてる分野
  - 高負荷 API
  - インフラ寄り処理

## AI 時代の影響

- AI がコードを書く時代に
  - フレームワーク差は縮小
  - AI（GitHub Copilot, Claude 等）は、多様なフレームワークのベストプラクティスを学習していルため、エンジニアが特定のフレームワークに精通する必要性が減少した。
  - 設計がより重要に
    - 最終的な「要件定義」「アーキテクチャ設計」「意図の汲み取り」は人間の領域
    - 実装が自動化されるからこそ、設計の良し悪しがシステムの成否を分ける

## 評価されるエンジニア像

- 1 つの技術に固執しない
- なぜそれを選ぶかを説明できる
- 用途とトレードオフを理解している

## まとめ

- フレームワーク差は縮小しているが明確な正解はなく、用途最適化が最大の価値
- 技術選定や設計が重視
- 2026 年現在、Rails を選ぶ理由
  - ビジネス価値を最短で安定して出したいなら、Rails が最も適している
  - ビジネスロジックが書きやすい
  - 仕様変更に強い
    - 現実の開発では、要件は変わる、仕様は揺れる、締切は近い、が多く、Rails は後から直す前提で作りやすい。移行が楽。
  - 最初から完璧は求めない現場で強い
  - 少人数チーム・個人開発・スタートアップに最適
  - 長い歴史があるため成熟していて事故が少ない、ノウハウが多い、変な落とし穴が少ない
    - 安定して動かしたいなら安心感がある
- 現代は Rails で全部やらないのが前提。
