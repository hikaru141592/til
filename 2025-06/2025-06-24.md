## 学習内容1  
- **タグ**: CI, テスト
- **タイトル**: .github/workflows/ci.ymlを作成する
- **内容**:  
1. GitHub ActionsのUI上でジョブセット全体を識別するときに表示されるname:を定義する
```
name: CI
```
2. トリガー（いつ動かすか）を決める
on:セクションに動かすタイミングを書く。例えば、
  - push: あるブランチにプッシュされたとき
  - pull_request: PRが作られたり更新されたとき 
  - ファイルの更新をした後にciジョブを実行したい場合、プッシュを介さずに実行する方法はない。
```
on:
  pull_request:
  push:
    branches: [ main ]
```
3. ワークフローがGitHub APIを呼び出すときの権限を設定
```
permissions:
  contents: write
```
  - contents: writeは「リポジトリの内容（コミットやタグなど）を書き込む権限」を有効化。
4. CIで何を自動化したいかをリストアップし、それぞれをjobとする
```
jobs:
  scan_ruby: # job名
    runs-on: ubuntu-latest # rus-onについては後述
    steps: # stepについては後述、上から順に複数のstepを記述する
      - name: Checkout code
        uses: actions/checkout@v4
```
  - RSpec、Minitest等のテスト
  - RuboCopでコード品質チェック
  - データベースが問題なく作成・マイグレーションできるか
  - PostgreSQLなどテスト用DBの起動（CIの仮想環境内でテスト用DBを起動する設定を作る）
  - LSecurity Scan
  - デプロイ処理（自動デプロイは本番環境に意図せずデプロイされるリスクもあるため、ステージング環境を別アプリで用意してから段階的に自動化するのがいい）
5. ジョブごとに設定として記述するもの
  - `runs-on`: 実行環境（Runner）を選ぶ。RailsやDockerを動かすには、Ubuntuランナーが一般的。
    ```
    runs-on: ubuntu-latest
    ```
  - `env`: 必要に応じて環境変数を設定
  - `services`: テスト実行中に必要な外部サービスをコンテナで立てる設定。テストjobでDBを起動する場合などに使用。
6. 各ジョブごとに、「どういうステップをどういう順で行っていくかを」定義する
```
    steps: # stepについては後述、上から順に複数のstepを記述する
      - name: Checkout code #ステップ名
        uses: actions/checkout@v4 # 使用するアクション、ここでは「GitHubリポジトリの最新コードをチェックアウト（取得）する公式アクション」を仕様
```
  - `with:`でアクションにパラメーターを渡すことが可能
  - `uses:`以外にも`run:`でシェルコマンドの実行が可能
