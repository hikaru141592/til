## 学習内容1  
- **タグ**: CI, バインドマウント
- **タイトル**: バインドマウント
- **内容**:  
ホストマシン（自身のPCやCIランナー）のファイル／ディレクトリを、コンテナの内部パスにそのまま紐づける機能のこと。  
ホストで持っているソースコードやキャッシュ済みのgemを、コンテナ内からも同じ内容として使いたいときに使える。  
コンテナとホスト間でファイルを同期させることで、ホスト側にキャッシュを保存・再利用できる。  
- 利用例
  - GitHub Actionsのランナー上にキャッシュしたvendor/bundleを、コンテナの/usr/local/bundleにバインドマウントすることで初回にキャッシュを復元し、コンテナ内でbundle installしてもホスト側にgemが残り次回以降のジョブでほぼインストールが不要となる。

## 学習内容2  
- **タグ**: CI, レースコンディション
- **タイトル**: レースコンディション
- **内容**:
複数の処理（スレッドやコンテナ起動など）が「どちらが先に終わるか・起動するか」に依存してしまい実行結果やタイミングが不安定になる状態。  
想定では「Aが終わったらBをする」つもりでも、実際にはBが先に走り始めてエラーになったりする。  
再現性が低く、たまたまタイミングが合うと成功して見えることがあるが、これは本番では落ちる恐れがある。  
- 例
  - `docker compose up -d db`でデータベースコンテナをバックグラウンド起動後、すぐ`rails db:create`や接続テストをする
  - DBがまだ「ソケットはListenしているが接続を受け付けていない」状態でエラーが起きる
  - 起動後に明示的に接続可能になるまで待つ（pg_isready -U ユーザ -t タイムアウト秒 など）処理を入れて、本当にDBが準備完了してから次のコマンドを実行するようにすることで対策可能。


## 学習内容3  
- **タグ**: CI
- **タイトル**: CIのtestジョブでDB起動・接続エラーが起きたときの対応
- **内容**:
  - 状況
    - `docker compose up -d db`は成功しているが、直後の`pg_isready`がno responseによりExit code 2になりタイムアウト
  - 対応
    - `.github/workflows/ci.yml`でエラーが出たSTEPの直後に`docker compose logs db`の処理を入れる。
      - `db`コンテナの標準出力／標準エラー出力ログをすべて表示 
      - Postgresの「初期化」「起動」「エラー」メッセージを確認
      - ボリューム権限エラーやクラッシュが起きていないかを把握
    - `.github/workflows/ci.yml`でエラーが出たSTEPの直後に`docker compose exec db netstat -plnt`の処理を入れる。
      - `db`コンテナ内でTCPのLISTENソケット情報を表示  
        - `-p`：プロセス名／PID  
        - `-l`：LISTEN状態のみ  
        - `-n`：数値表示（ホスト:ポート）  
        - `-t`：TCPのみ   
      - PostgresがTCPポート5432で正しく待ち受けているかを確認
    - 上記の追加デバッグ用ジョブを`if: always()`とし、直前のジョブがエラーでも実行されるようにする。
    - netstatが公式Postgresイメージに入っていないため、コンテナ内で呼んだ際にnot found、他のコードで代替する。
      - `docker compose exec db psql -U hikaru -c '\conninfo'`: 接続可能かどうかをpsqlでチェック
      - `docker compose exec db pg_isready -U hikaru -d hikaru_test`: pg_isreadyでも改めて確認
    - 以上のデバッグ用コード追加により得られた結果
      - Initdb（クラスタ初期化）は完了、データディレクトリのセットアップ自体は終わっている。
      - Postgresサーバー本体（postmaster）がまだ「待ち受けソケット」を出していない、ソケットファイルが存在しないということは、サーバープロセスがまだ起動していない（またはソケットの場所が違う）ということ。
      - pg_isready/psqlいずれもサーバー起動待ちで失敗している
    - `docker compose exec db pg_isready -U hikaru -t 30`としていたが30秒以上に秒数増やす修正
      - pg_isreadyはサーバーに1回接続を試み、成功（接続を受け付ける状態）なら終了コード0、失敗（まだ起動中／パスワード不一致／ホスト名誤りなど）なら1または2を返すコマンド。
    - 150秒にしてみたら接続成功

## 学習内容5  
- **タグ**: CI
- **タイトル**: CIで「KeyError: key not found: "DATABASE_URL" (KeyError)」
config/database.ymlのproductionセクションのurl: <%= ENV.fetch("DATABASE_URL") %>が未定義ということでKeyErrorが発生。  
  - 本番環境用の環境変数はHeroku定義なのでデフォルト値を用意するか、url: <%= ENV["DATABASE_URL"] %>（変数が未定義ならnullとする）に書き換える
  - Rspec等を実行するジョブなのでproductionセクションは一見関係なさそうだがconfig/database.ymlファイル全体を ERB（<%= … %>） として評価してYAMLに変換するので、productionセクションのurl: <%= ENV.fetch("DATABASE_URL") %>が未定義でもエラーとなる。
